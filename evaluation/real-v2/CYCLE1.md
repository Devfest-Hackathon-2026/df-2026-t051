# サイクル1：採用前の根拠と変更

基準：development-baseline、60枚182値。数値・カテゴリ182/182、schema60/60、タイトル53/60、単位39/60、完全一致35/60。
単位不一致のうち非null値と併用した15画像51セルをB候補として検出。単位の分母省略、指数説明の欠落、観測年の混入、単なる語彙差を含むので、51件の実際の倍率事故とは呼ばない。タイトル7画像に副題・観測年が連結された。

既知の日本語3枚は今回schema3/3で、過去のValidationErrorを再現しなかった。過去の原文応答が保存されていないため、原因は未特定のまま。現行保留処理により9/15値がnull。これは桁・単位の省略が曖昧な場合の安全保留であり、9件の不適切なnullと断定しない。

異常系は14枚をモデルが拒否し、1枚は1200万画素上限でモデル呼出前に422拒否。旧採点器が前処理拒否を失敗と数えたため、HTTP 413/415/422による異常入力の安全停止を別に採点する修正を追加。元のanomaly-baseline記録は保持し、anomaly-input-filter-check（API生成0回）で1枚の実際の422を確認した。正常系の採点には影響しない。

## 変更と採用理由

1. 汎用PROMPTで主見出しと副題・出典・観測年を区別し、単位に印刷された倍率・分母・指数基準を保持するよう指示。特定のカテゴリ、正解値、画像IDは埋め込まない。
2. Decimalによる数値根拠照合をAPIへ接続。原文とモデル値が不一致ならnull。明示された単位同士だけを一意に換算し、単位省略と複合桁表記が曖昧ならnull。すでにnullの値は昇格させない。元の根拠・unitを保持し、教員へ警告する。
3. 同じGeminiモデルのthinking LOW・最大出力8192へ設定。旧日本語の重い推論（今回API平均30.282秒）と出力余裕への予防策。過去のschemaエラーの根本原因を修正した証拠とは扱わない。JSON修復・型強制・切断出力の補完はしない。
4. SDKの隠れた再試行を無効化。評価器は429だけ上限付きで明示的に再試行する。

採用前のローカル回帰：Python134件成功。数値正常化は単体・API境界で検証。実データでの前後差はdevelopment-cycle1で別記し、結果が出る前に改善成功とはしない。本番未反映。

ベースライン等の78生成要求で429がなく、プロジェクトquotaのpaid metric（1000要求/分、入力200万token/分）を確認した上で、次の試験では開始間隔を5.1秒から1.1秒へ短縮する。同時処理2と費用上限は維持。待機込みの総時間は条件が異なるため性能比較に使わず、待機を除く生成HTTP時間で比較する。
